# The analyst (`pulse ask`)

A question in English or Turkish is answered from the warehouse, with its SQL,
its rows and the evidence every number in the sentence was checked against -
or refused with the reason. This page describes how it decides, what it
checks, and how well it does on questions it was not built for.

## How a question is answered

1. **What is asked** (`brain/intent.py`, independent of the router): the apps
   (ids, display names, typos within a small edit distance, "the puzzle game"),
   names that look like an app but are none, ad networks, platforms, stores,
   countries, app versions, device tiers, levels, ad formats, the period
   ("yesterday", "15 Ekim 2026", "son 14 gün", "last week", "since ...", a
   month), metric words nobody collects (NPS, K-factor) and the shape of the
   question (why, trend, comparison, ranking, total). Turkish case endings
   after an apostrophe or glued to a name ("Meta'daki", "Almanyada") are read.
2. **Early refusals**: an app that does not exist, an ambiguous genre, a metric
   nobody collects, and a filter value with no rows for the app ("quartz_merge
   has no data for network = Meta. Values with data: tiktok, unity_ads,
   organic.") never reach a query.
3. **Routes**, cheapest and most trusted first: the verified-query library;
   driver analysis for "why" questions; the metric catalog with every filter
   applied (a metric can move to a finer source model to do so: UA spend by
   country and platform comes from `stg_ua_spend`, activity by platform from
   `stg_active_users`, retention by platform / country / version / source /
   tier from the cohort_dims pull), portfolio totals, rankings, trends against
   the previous period of the same length and the dashboard's headline figure
   next to a period answer; only with a model configured, a model-written
   SELECT (AST guard, locked read-only DuckDB session).
4. **The consistency gate** (`brain/consistency.py`) runs on every answer,
   whichever route produced it.

## Question-evidence consistency

`verify.py` proves that every number in an answer equals a value of its
evidence. On 14 Nov 2026 an audit showed that this is not enough: "What is the
CPI on Meta for quartz_merge?" was answered with $0.413, the blend of TikTok
and Unity Ads, every number verified - the router had dropped the network
filter and quartz_merge has no Meta spend at all.

The gate reads the evidence SQL (sqlglot, with the bound parameters
substituted) and its result rows, and checks each filter of the question:

- app, ad network, platform, store, country (ISO codes and English names are
  the same country), app version, device tier, level, ad format: an equality
  or `IN` predicate with exactly the asked values, result rows that hold only
  those values, or a table whose every row has the value (Android vitals are
  Android / Google Play);
- the period: the evidence's date range (predicates on `date` /
  `cohort_date`, or `first_day` / `last_day` / `date` in the rows, or the
  window of a snapshot table such as the 30-day UA summary) must equal the
  asked one, cut at the newest data day;
- "total" must be one number, "which network / level / app" must come with
  that breakdown.

A gap turns the answer into a refusal that names it ("I can't apply platform =
iOS to net revenue: the tables it comes from do not carry that split, and the
unfiltered number would answer another question."). A verified query that
does not cover the filters falls through to the catalog instead.

## Why questions

`brain/drivers.py`. The change is the current period against the one before
it (the last 7 days against the 7 before; for retention the newest 7 complete
cohorts against the 14 before), split by what the warehouse has for the metric:

| Metric | Split |
|---|---|
| D1 / D7 / D30 retention | `insights.cohorts.explain`: Kitagawa mix/rate, Adtributor and DIFF-lite (`brain/attribution.py`) over platform, country, app version, first-touch source, device tier |
| crash-free users / sessions, sessions per DAU, engagement | exact Kitagawa split by platform |
| DAU, new users, sessions | each platform's share of the change |
| net revenue | IAP against ads |
| UA spend, network installs, CPI | by network |
| frame time, memory | the device tier that moved most, then the newest version of that tier |

A release that first appeared inside the current period is named for every
metric, because tables such as the crash counts carry no version. Every answer
ends with the caveat the insight engine uses: an association in time, not a
measured cause.

## The semantic layer

`brain/semantic.py` builds one description of every metric from the catalog
(`metrics.yaml`), the formulas of [METRICS.md](METRICS.md)
(`brain/metric_docs.yaml`, generated by
`python -m studio_pulse.brain.semantic --write`; a test fails when it is out
of date), the grain, time column and window of every model (tests check each
grain is unique on the demo) and the warehouse itself (the stored values of
every filter column). The model sees one line per metric - definition, table
and column, how rows combine, time or window, filters and the finer tables
that add more - plus tables, join paths, rules and today's date, instead of a
raw dump of 90 tables (about 15k tokens).

Every catalog metric, so every `model.column` of METRICS.md, has a question in
`brain/eval/reach.yaml`; the test asks each without a model and requires an
answer from that metric's table.

## Evaluation

```
pulse demo --workdir .pulse-demo
pulse ask --eval --config .pulse-demo/pulse.yaml [--set holdout|holdout_b|dev|all] [--no-llm] [--details] [--json]
```

The command exits 1 when any answer is confidently wrong.

### The question sets

| Set | File | Questions (groups) | Written | Tuned on |
|---|---|---|---|---|
| golden | `eval/golden.yaml` | 57 (25) | with the router (12 Nov) | yes: in-sample |
| dev | `eval/dev.yaml` | 91 (66) | 14 Nov, before the changes | yes |
| holdout A | `eval/holdout.yaml` | 124 (85) | 14 Nov, before the changes | **never** |
| holdout B | `eval/holdout_b.yaml` | 50 (35) | 14 Nov, after the changes | **never** |

A bank of 199 questions (140 groups, TR and EN) was written from METRICS.md and
the demo warehouse schema before the router's patterns were read: activity,
retention by platform / country / version / source / tier, revenue, LTV and
pLTV, stability, performance, levels, UA by network / country / platform,
reviews, experiments, SDK metrics, freshness, and adversarial questions
(non-existent apps, networks, countries, levels and platforms, missing
periods, the future, ambiguous periods and apps, typos, Turkish suffixes,
mixed language, metrics nobody collects, "why"). It was split by group, so
every phrasing of one question is on the same side: per kind (value / refuse /
why), groups are ordered by `sha256("studio-pulse-holdout-v1:" + group)` and
the first ceil(60%) are held out. The audit's 16 probe questions were already
seen and are in dev only. Set B (50 more questions) was written after the
router changes and frozen before it was run on them.
`tests/brain/test_brain_accuracy.py` pins both holdout files' hashes,
recomputes the split rule, and fails if a phrasing also appears in golden,
dev or reach.

Ground truth is SQL in the set (`truth`, one or more fair readings such as the
three meanings of "last week"; `absent` returning 0 for data that does not
exist; `driver` returning the segment a "why" must name), run by the test, not
typed. Grades: **right** (every required value or label of one reading appears
in the text, or in a result table of at most 5 rows; a refusal for `absent`
items; the driver named for "why"), **partial** (some of them, or only in a
large table, or a "why" without the driver), **refused**, and **confidently
wrong** (numbers stated, none of them the truth, or numbers for data that
does not exist).

The last Gemini rows reuse the client's content-hash cache for prompts that did
not change between the two "after" runs; one inspection round on the model route
also found a generated query that read "yesterday" as the day before the newest
data day, which the period check now catches (a dated table whose query shows no
date range is refused as unchecked).

The router-only runs cost nothing; the model runs above cost USD 0.23 in
total (the shared client's ledger), well under the USD 1 budget.

Intervals are Wilson 95% per question. Phrasings of one group are correlated
(the same question in two languages), so the effective sample is closer to the
number of groups and the true intervals are somewhat wider.

### Honest notes

- Holdout A's baseline failure list was printed once, before the work, while
  the grading script was checked. Every change after that was driven by the dev
  set, the reachability test (METRICS.md) or the golden set; set B exists to
  measure the result on questions that could not have steered it.
- The "after inspection" rows are tuned on the questions they report, like
  dev; the clean rows above them are the held-out result. `tests/brain/
  test_brain_accuracy.py` keeps the router-only result as a regression guard
  (confidently wrong must stay 0).
- Everything is measured on the synthetic demo warehouse; real data has other
  values, longer names and gaps.
- The model's answers vary run to run even at temperature 0; the LLM numbers are
  one run each.
